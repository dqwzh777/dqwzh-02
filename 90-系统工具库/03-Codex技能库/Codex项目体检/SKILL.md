# Codex 项目体检系统

> 用途:保持 AGENTS.md、README、项目说明和真实项目状态一致,防止 AI 协作基于过期前提。

## 一飞版说明

这个 skill 表面上是项目自检,底层是在训练一个习惯:所有 AI 项目都要有入口、有地图、有状态、有缺口。

适合用在这些场景:

- 你的知识库、课程包、客户档案更新了,但总说明没有同步。
- 你新增了 skill、目录或资料入口,不确定新手能不能找到。
- 你把资料给 Codex 用,但它总是引用旧路径、旧价格、旧版本。
- 你想把自己的项目从"一堆资料"变成可交接、可复盘、可复制的业务资产。

## 适用对象

任何使用 Codex / Codex App 管理业务资料、课程资料、客户项目或个人知识库的人。这个 skill 不要求你会写代码,它检查的是"项目说明是否跟真实资料对得上"。

## 核心原则

1. 先看真实文件,再看说明文件。
2. 只检查事实一致性,不凭感觉重写项目。
3. 发现问题先列清单,再给修改建议。
4. AGENTS.md / README / 项目说明属于入口文件,影响面大,修改前要让用户确认。
5. 每次体检都要输出"已成行 / 未成行 / 缺口"。

## 触发方式

用户说以下任意一种,就进入本流程:

- "执行Codex项目体检"
- "项目自检"
- "AGENTS.md体检"
- "帮我看看这个知识库入口清不清楚"
- "检查一下这个项目说明有没有过期"

## 体检前先确认

先问或自行识别三个信息:

- 项目根目录在哪里?
- 入口说明文件有哪些?常见为 `AGENTS.md`、`README.md`、`00-先看这里.md`、`当前项目状态.md`。
- 本次是只读体检,还是允许按确认结果修改文件?

如果用户没有明确授权修改,默认只读体检。

## 机械检查清单

### 维度1:目录地图一致性

对照入口文件里的目录描述和真实目录:

- 说明里列了但实际不存在的文件夹。
- 实际存在但说明没提到的关键入口。
- 文件夹改名后,旧名字还残留在说明里。
- 新手第一步应该打开的文件是否明确。

推荐命令:

```bash
find <项目根目录> -maxdepth 3 -type d | sort
rg -n "入口|目录|地图|先看|使用说明|当前项目状态" <项目根目录>
```

### 维度2:任务入口有效性

检查用户常用任务是否有清楚入口:

- 新资料放哪里。
- 客户资料从哪里开始填。
- 内容选题、口播、公众号、小红书等输出从哪个 skill 开始。
- 客户案例、评论区、客诉、成交记录应该入哪个库。
- 旧资料是否需要迁移或标记状态。

### 维度3:skill / 工具说明一致性

对照 skill 列表和说明文件:

- skill 文件夹是否都存在 `SKILL.md`。
- skill 的 `name`、`description` 是否仍是旧项目或旧联系人。
- 是否还残留不适合当前交付工具的说明,比如旧平台、旧路径、旧命令。
- 入口文件是否提到了已经删除或改名的 skill。

推荐命令:

```bash
find <项目根目录> -name SKILL.md | sort
rg -n "name:|description:|微信|联系人|Codex|AGENTS|README" <项目根目录>
```

### 维度4:业务数据一致性

检查说明里的业务事实是否过期:

- 名字、微信号、公司名、课程名、产品名。
- 价格、交付周期、适合人群、不适合人群。
- 案例数据、客户行业、服务范围。
- 课程定位和实际学员是否一致。

### 维度5:状态描述准确性

检查"已完成 / 进行中 / 待补"是否真实:

- 文件写着已完成,但内容还是空模板。
- 文件写着待补,但实际已经有正式内容。
- 有些入口还没成行,但说明里讲得像已经完善。
- 客户版、公开版、内部版是否混在一起。

### 维度6:记忆 / 项目说明冲突

如果项目有记忆文件、阶段复盘或当前项目状态,逐条检查:

- 记忆里已经更新的定位,入口文件是否还停在旧定位。
- 重要协作偏好是否需要进入 AGENTS.md。
- 客户标准、资料来源、应用标签是否和当前模板一致。
- 哪些内容只应留在内部,不适合放到公开下载包。

## 输出格式

```markdown
# Codex 项目体检报告

## 1. 总判断
- 当前入口是否清楚:
- 新手是否能找到第一步:
- 最影响使用的 3 个问题:

## 2. 已成行
- ...

## 3. 未成行
- ...

## 4. 需要修改
| 文件 | 问题 | 建议 |
|---|---|---|
|  |  |  |

## 5. 需要用户确认
- ...
```

## 修改规则

如果用户确认允许修改:

1. 只改入口、说明、状态、路径、旧称呼这类事实问题。
2. 不顺手重写业务内容。
3. 不删除用户资料。
4. 修改后再跑一次关键词检查。
5. 最后报告"改了什么 / 还缺什么 / 下一步先做什么"。

推荐检查:

```bash
rg -n "旧项目名|旧联系人|旧工具名|TODO|待补|未成行" <项目根目录>
find <项目根目录> -name ".DS_Store" -delete
```

## 完成口径

体检完成后,不要只说"已完成",要把下一步说清楚:

- 哪些入口现在已经能给新手用。
- 哪些入口只是先占位,还需要下午或下一轮补。
- 哪些资料必须由用户本人补,AI 不能编。
