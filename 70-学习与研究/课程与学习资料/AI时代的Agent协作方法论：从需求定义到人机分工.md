# AI 时代的 Agent 协作方法论

> 从一场飞书 Agent 实操演示中，提炼可复用的工作方法、系统架构与行动清单。

## 一、这份分享真正讲了什么

这场分享表面上演示了多维表格搭建、短视频抓取、文档修改、点餐、语音生成等功能，核心其实只有一句话：

> AI 时代的竞争力，不是拥有某个最强模型，而是能否把业务、模型、Agent、Skill、脚本和数据工具组合成稳定的工作系统。

完整链路可以概括为：

1. 先把业务需求写清楚，而不是立刻动手搭系统。
2. 根据任务的规则性和复杂度，选择脚本、小模型或 Agent。
3. 把外部信息抓进统一的数据环境，再用 AI 加工。
4. 让 Agent 像同事一样交付成果、接受评论并迭代。
5. 人保留最终判断、验收和核心手艺，不把注意力完全交给 AI。

## 二、核心认知一：先写 PRD，再开始执行

分享中的第一个关键动作不是“搭表”，而是先生成 PRD（产品需求文档）。

### 为什么要先写 PRD

AI 执行失败，很多时候不是能力不够，而是双方对目标的理解不一致。PRD 的作用是把模糊想法转化为可以共同确认的执行合同：

- 要解决什么问题；
- 谁会使用；
- 包含哪些功能；
- 数据如何流转；
- 什么结果才算完成；
- 哪些内容不在本次范围内。

### 推荐的 AI 项目启动流程

```text
模糊想法
  ↓
AI 追问并形成 PRD
  ↓
人工审核、增删需求
  ↓
AI 展示修改差异（diff）
  ↓
人工确认
  ↓
开始搭建
  ↓
按验收标准检查
```

### 可直接复用的提示词

```markdown
我想搭建一个【系统/工具名称】，主要服务于【用户】，解决【问题】。

请先不要执行，先为我输出一份 PRD，至少包括：
1. 背景与目标
2. 用户角色与使用场景
3. 核心业务流程
4. 功能模块与优先级
5. 数据表及关键字段
6. 自动化规则
7. 权限设计
8. 验收标准
9. 暂不包含的范围
10. 仍需我确认的问题

我确认 PRD 后，你再开始搭建。后续需求发生变化时，请先展示修改差异，再等待我确认。
```

### 学习结论

真正重要的不是“会不会搭表”，而是能否把业务过程表达成清晰的目标、对象、规则、数据和验收标准。

## 三、核心认知二：任务要分三层

分享中最有价值的方法，是根据任务性质选择不同执行者。

| 任务层级 | 任务特征 | 最合适的执行方式 | 示例 |
|---|---|---|---|
| 第一层 | 高度标准化、规则明确、步骤固定 | 脚本 / RPA / 自动化 | 打开网页、点击、抓取链接、搬运数据、定时同步 |
| 第二层 | 需要一定语义理解，但判断相对简单 | 小模型 + Skill | 分类、打标签、字段提取、摘要、格式转换 |
| 第三层 | 开放、复杂、需要泛化和综合判断 | Agent / 强模型 | 洞察爆款规律、设计方案、写 PRD、战略分析、内容创作 |

### 核心原则

> 能用脚本稳定完成的任务，不要交给 Agent；只有需要理解、判断和创造的部分，才使用 Agent。

原因包括：

- 脚本成本更低、速度更快；
- 规则任务由脚本完成，结果更可预测；
- Agent 在固定步骤上容易出现随机偏差；
- 把昂贵模型留给高价值判断，整体系统更经济。

### 判断任务该交给谁

可以连续问四个问题：

1. 每一步能否明确写出来？能，优先脚本。
2. 输入不同，但判断标准是否固定？是，考虑小模型 + Skill。
3. 是否需要跨信息综合、权衡和生成新方案？是，使用 Agent。
4. 出错是否会造成付款、发消息、删数据或权限泄露？是，增加人工确认。

## 四、核心认知三：组合器比单一工具更重要

分享者强调，AI 时代的“必杀技”不是某一个模型，而是组合能力。

一个典型的内容生产系统可以这样构成：

```text
RPA/脚本抓取公开视频
        ↓
多维表格存储链接和元数据
        ↓
ASR 将视频转成逐字稿
        ↓
小模型进行分类、打标和字段提取
        ↓
Agent 跨样本分析标题、结构与话术
        ↓
生成文档或口播初稿
        ↓
人工审阅、评论和校正
        ↓
AI 修改并生成语音、视频等衍生物
```

### 组合系统的六类组件

- **数据源**：群消息、视频、会议纪要、客户记录、业务系统。
- **采集层**：API、RPA、浏览器自动化、定时工作流。
- **存储层**：数据库、多维表格、文档库、知识库。
- **处理层**：ASR、OCR、分类、打标、清洗、摘要。
- **推理层**：Agent 负责分析、规划、生成和跨工具协作。
- **交付层**：文档、表格、仪表盘、消息、音频、视频。

系统设计时，应先画清数据如何流动，再决定每个节点使用什么工具。

## 五、核心认知四：Skill 是把经验封装成能力

分享中的 Skill，可以理解为给 Agent 安装的一套专项说明书和工具接口。它把原本依赖人工记忆和操作的流程，封装成可重复调用的能力。

### Skill 通常包含什么

- 适用场景；
- 操作步骤；
- 输入和输出格式；
- 工具或 API 的调用方式；
- 判断规则；
- 异常处理；
- 权限和安全边界；
- 示例。

### 从工具到 Skill 的演化

```text
人手动使用工具
→ 把固定步骤写成脚本
→ 把脚本、说明和判断规则封装为 Skill
→ Agent 根据自然语言自动调用 Skill
```

### 适合优先 Skill 化的工作

- 高频重复；
- 流程相对稳定；
- 输入和输出明确；
- 已有成熟操作经验；
- 出错容易检查和回滚。

### 初始化配置的本质

分享中让另一个 AI 生成若干 Markdown 配置文件，本质是先把“我是谁、Agent 是谁、要做什么、如何协作”写成持久上下文。可采用如下结构：

```text
SOUL.md       角色、价值观、表达风格
AGENTS.md     Agent 的职责、流程和协作规则
USER.md       用户背景、偏好、业务目标
TOOLS.md      可用工具、权限和调用限制
MEMORY.md     长期有效的事实与经验
```

文件名并非重点，重点是把隐性要求外化为可维护的文字。

## 六、核心认知五：Agent 应按“数字同事”来管理

分享者没有把 Agent 当成一次性问答工具，而是当成飞书里的同事：

- 给任务；
- 收文档；
- 在具体位置留评论；
- 要求根据评论修改；
- 修改后解决评论；
- 再做验收。

### 更有效的协作闭环

```text
委派 → 交付 → 评论 → 修改 → 验收 → 沉淀为模板或 Skill
```

### 好反馈的写法

不要只说“写得不好”，而要指出：

- 哪一段有问题；
- 问题是什么；
- 判断依据是什么；
- 希望朝哪个方向修改；
- 修改后的验收标准是什么。

示例：

```markdown
当前标题分类过于抽象，无法直接指导创作。
请将分类改成可识别、可套用的具体类型；每类补充：
1. 适用场景
2. 典型结构
3. 为什么有效
4. 一个新写的示例

修改完成后，请逐条回复本评论并标记为已解决。
```

### 为什么“过程透明”重要

PRD、任务列表、执行步骤和修改差异被展示出来，是为了让 AI 的执行从黑盒变成可观察流程。透明化有三个作用：

- 尽早发现理解偏差；
- 知道任务卡在哪里；
- 方便人随时介入和纠偏。

## 七、核心认知六：AI 降低的是工具门槛，不是业务门槛

过去搭建业务系统，需要掌握 Excel、数据库、表格配置和界面拖拽。AI 会逐步降低这些操作门槛，但不会替代以下能力：

- 理解真实业务；
- 梳理业务流程；
- 定义关键字段和指标；
- 识别异常情况；
- 设计权限和责任；
- 判断结果是否真正可用。

因此，当所有人都能通过自然语言搭工具时，不懂业务的人反而更容易暴露。新的竞争力是：

> 能否把业务讲清楚，并把它翻译成 AI 可以执行、可以验收的系统。

## 八、核心认知七：必须给人保留“无 AI 时间”

分享者指出一个很真实的问题：多个 Agent 同时工作，会制造大量待读取、待判断、待确认的输出。人看起来启动了很多任务，但注意力被不断切换，最终没有把任何一件事真正推进。

### 建议：每天设置两小时无 AI 深度工作

这两小时主要做三件事：

1. 集中阅读和验收 AI 的输出；
2. 选择少数高价值成果继续推进；
3. 精进自己最核心、最不可外包的专业手艺。

### 人机工作的节奏

```text
AI 并行收集和生成
       ↓
人集中阅读、判断和精修
       ↓
将明确的新任务再交给 AI 或同事
       ↓
进入下一轮异步执行
```

AI 擅长扩大产出，但人必须控制进入自己注意力的内容数量。否则“生产力提升”会变成“信息债务增加”。

## 九、案例拆解

### 案例 1：自然语言搭建多维表格系统

**过程**：描述需求 → AI 写 PRD → 人增加“业绩预测模块” → AI 展示差异 → 人确认 → AI 搭建数据表、仪表盘、工作流和权限。

**学习点**：

- 需求确认应在实施之前；
- 中途变更要可追踪；
- 验收不只看表格，还要看流程、权限和仪表盘；
- AI 可以降低配置成本，但业务结构仍由人负责。

### 案例 2：抓取并分析短视频

**过程**：RPA 抓取 12 个高赞视频 → 写入多维表格 → ASR 提取逐字稿 → Agent 分析标题和话术 → 生成飞书文档 → 人留评论 → Agent 修改。

**学习点**：

- 抓取是规则任务，交给脚本；
- 转写和打标是轻语义任务，可批量自动化；
- 跨样本洞察是复杂任务，交给 Agent；
- 最后必须由懂内容的人验收。

### 案例 3：对话完成点餐

**过程**：Agent 调用点餐接口 → 读取配送地址 → 根据热量和预算推荐 → 创建订单 → 人完成支付 → Agent 查询配送状态。

**学习点**：

- 产品交互可能从“人操作 UI”转向“Agent 调用服务”；
- 服务会越来越 API 化、命令化、Skill 化；
- 支付、地址、订单等高风险动作仍需明确授权和确认。

### 案例 4：AI 生成数据可视化组件

**过程**：用户描述所需图表 → AI 读取底层数据 → 生成原本系统没有的交互式图表组件。

**学习点**：

- 底层数据结构和权限仍然重要；
- 表层界面和可视化的生成成本会快速下降；
- 未来产品可能分成稳定的数据底座和动态生成的交互界面。

## 十、对未来产品与组织的推演

### 1. 产品从“服务人”转向“同时服务人和 Agent”

产品可能越来越呈现以下形态：

- API 化；
- 命令行化；
- Skill 化；
- 弱 UI 或去 UI 化；
- 数据和权限成为核心底座；
- 界面由 AI 按需生成。

这不一定意味着 UI 会消失，而是很多操作不再必须由人亲自点击。

### 2. 组织从“人管理工具”转向“人和 Agent 共同生产”

随之出现的新问题包括：

- 员工创建的 Agent 产出归谁；
- 员工离职后，Agent、记忆和 Skill 如何移交；
- Agent 以谁的身份访问数据；
- Agent 误发消息、误操作时谁负责；
- Agent 的工作如何计量、审计和评价；
- 哪些权限可以长期授予，哪些必须逐次确认。

这些不只是技术问题，还涉及治理、劳动关系、知识产权和信息安全。

## 十一、需要警惕的风险

原分享偏现场演示和产品推广，学习时需要把“可演示”与“可稳定用于生产”区分开。

### 1. 权限风险

Agent 以用户身份读取群聊、修改文档或发送消息，能力越强，越需要最小权限、操作日志、有效期和审批机制。

### 2. 隐私与合规风险

抓取平台内容、读取群消息、使用个人音色、处理客户信息，都可能涉及平台规则、著作权、个人信息和内部数据合规。

### 3. 自动执行风险

付款、下单、群发、删除、权限变更等动作不应仅凭模糊自然语言自动执行，必须设置确认节点和额度边界。

### 4. 幻觉与错误完成

Agent 可能声称“已经完成”，但实际结果不完整或有误。验收应基于可查看的产物、数据和日志，而不是对话中的口头汇报。

### 5. 成本与注意力风险

Token 成本可能下降，但审阅成本不会自动消失。并行启动过多 Agent，可能让人陷入新的信息过载。

### 6. 术语和转写误差

原文来自自动转写，其中产品名、人名和英文术语存在明显误识别，例如 “OpenCall”“Cloud Code”“SO.md”等可能不是准确名称。涉及安装、采购或权限配置时，应以产品官方文档为准。

## 十二、可落地的行动清单

### 第一步：盘点工作

列出最近一周反复做的 10 项任务，并标记：

- 发生频率；
- 每次耗时；
- 是否有固定步骤；
- 是否需要专业判断；
- 出错风险；
- 可否验收。

### 第二步：进行三层分类

- 固定步骤：脚本 / RPA；
- 简单语义判断：小模型 + Skill；
- 复杂分析与生成：Agent；
- 高风险动作：无论由谁执行，都加人工确认。

### 第三步：选择一个最小闭环

不要一开始就做“万能 Agent”。选择一个高频、边界清晰、结果可检查的流程，例如：

```text
收集客户问题 → 自动分类 → 汇总高频问题 → 生成人工审核的选题建议
```

### 第四步：先写 PRD

明确输入、输出、流程、字段、权限、异常和验收标准。

### 第五步：搭建并保留人工节点

尤其在外发、支付、删除、权限变更和正式发布之前设置确认。

### 第六步：把成功流程沉淀为 Skill

记录提示词、工具、规则、异常和示例，让下一次调用更稳定。

### 第七步：每周复盘四个指标

- 节省了多少人工时间；
- 输出有多少真正被采用；
- 错误和返工发生在哪里；
- 人的注意力是否因此更集中。

## 十三、复习卡片

**Q1：为什么 AI 搭系统前要先写 PRD？**  
A：为了对齐目标、范围、流程和验收标准，降低执行偏差。

**Q2：什么任务优先使用脚本？**  
A：规则清楚、步骤固定、重复频繁的任务。

**Q3：什么任务适合小模型 + Skill？**  
A：需要语义理解，但判断规则相对稳定的分类、提取和打标任务。

**Q4：什么任务适合 Agent？**  
A：需要跨信息综合、泛化、权衡和创造的复杂任务。

**Q5：组合系统为什么比单一模型重要？**  
A：不同组件各有所长，合理分工能同时提高稳定性、产量并降低成本。

**Q6：AI 降低工具门槛后，什么能力更重要？**  
A：理解业务、表达流程、定义标准和判断结果的能力。

**Q7：为什么要保留无 AI 时间？**  
A：用于集中验收 AI 输出、做高价值选择，并精进人的核心专业能力。

**Q8：Agent 获得用户身份权限时最重要的原则是什么？**  
A：最小权限、全程可审计、高风险动作人工确认。

## 十四、一页总结

```text
先业务，后工具
先 PRD，后执行
规则任务给脚本
轻判断给小模型 + Skill
复杂任务给 Agent
高风险动作留人工确认
所有成果都要验收
成功流程沉淀成 Skill
用 AI 扩大产能，用人的手艺保证质量
```

最值得记住的最终结论是：

> AI 不是替你完成一切的魔法，而是一支需要被定义目标、合理分工、授予边界、持续反馈和严格验收的数字团队。
