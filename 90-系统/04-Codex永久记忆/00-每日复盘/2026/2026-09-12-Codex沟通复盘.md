## 项目更新

- WorkBuddy：公开资料指向“开放平台企业认证 → 切换企业主体 → 我的专家/创建专家团 → 提交审核”的路径。企业主体、营业执照、统一社会信用代码、法人及管理员实名认证仍需以登录后台实际页面和最终审核结果为准；公开入口与模板字段存在版本差异，未把可访问 URL 或模板下载当作已上架。
- 良财友道主体核验：公开报道对创始人/所长及关联公司的叙述不一致；上架主体应以营业执照、税务师事务所登记和品牌授权文件核对，不能直接写死个人或关联公司的身份关系。
- 良策 Web 应用：判断其核心可抽象为“组织/应用 → 页面分组 → 数据表 → 字段/记录 → 视图 → 关联 → 看板/流程 → 权限”。建议先做有限页面模板和飞书官方 SDK 连接器的业务应用生成器，再评估通用 AI Web Coding；不建议直接 fork Teable/APITable 作为商业核心。
- 开源参考：Teable适合研究 PostgreSQL + AI App Builder，APITable适合研究元数据/协作模型，Baserow/Appsmith适合视图、连接器和权限；许可证、维护状态及沙箱安全需在实际采用前单独核验。

## 新确认的偏好与决策

- 上架任务优先验证企业主体归属、审核入口和提交回执；“认证成功”“能打开发布页”不等于专家团已发布。
- 产品开发先拆底层数据与元数据模型、页面 DSL、权限和工作流，再进入代码；先验证一个可用业务场景，不追求一开始支持任意需求。
- 真实主体、客户案例和业务数据不虚构；第三方报道冲突时保留不确定性并要求一手材料。

## 可复用方法

- 把平台流程拆成“公开文档/登录入口/企业认证/草稿创建/提交审核/客户端市场验收”六个证据层级，逐层留证。
- 把多维表产品拆成数据层、元数据层、渲染层、连接器层和运行/部署层；先固定对象、字段、关系、状态和角色，再设计自然语言生成。
- 评估开源项目同时看功能贴合度、许可证、商业化边界、迁移成本、维护活跃度和安全隔离，不能只看演示效果。
