**项目交接文档**

版本 V0.1  |  编制日期 2026年9月16日  |  当前阶段 产品定义与范围澄清

### 交接结论

本项目旨在把企业 AI 入企项目的阶段、任务、资料、证据和决策集中管理，让负责人能够掌握进度，并让 AI 根据有来源的项目上下文辅助总结和准备材料。接手人应先验证真实工作流程和最小范围，再进入开发。当前没有依据认定软件已经建成、技术选型已经确定或业务验收已经完成。

## 01 项目背景与产品定位

### 业务背景与目标

【已确认事实｜S1 第一节】附件将元序智能定位为“企业AI市场增长系统提供者”，以良策积累的实体企业 IP 方法、客户场景和业务经验为入口，为实体企业、创始人 IP 和一人公司（OPC）搭建知识库、内容工作流、线索承接和经营复盘系统。这是附件版本中的定位，是否仍作为当前对外表述，应由业务负责人确认。

【已确认事实｜S1 第一节】业务边界包括：不只做工具培训、不做通用软件代理、不做数字人或短视频代运营、不一开始承诺全公司自动化；OPC 是渠道与试验场，不是唯一客户身份。

【已确认事实｜S1】首个验证闭环为“企业资料 → 知识库 → 选题或脚本 → 人工审核 → 发布或分发 → 线索收集 → 周度复盘”；首批项目也可从销售、交付、客服或内部管理的单岗位高频流程切入。工作台应能记录这些项目，但不代表第一版要执行整条内容生产和分发链。

### 当前已经明确到什么程度

【已确认事实｜S2 用户表述】要做一个在公司工作中有帮助的工作台，能够记录项目，并希望未来 AI 了解项目进展；用户考虑连接 Obsidian，但对数据库等方案尚无定论；希望页面具有良好的视觉体验。

【讨论建议｜S2】产品暂称“企业 AI 入企项目工作台”，作为统一项目事实源、企业知识库入口与 AI 项目助手。建议先服务内部项目团队，再考虑客户开放。这里确认的是方向已被提出，不代表产品定位和用户范围已经正式批准。

### 产品价值与验证问题

【本稿建议】优先验证三件事：负责人能否快速找到当前阶段和下一步；交接人能否从证据还原关键决策；AI 能否依据最新资料回答项目问题并标明来源。资料分散、重复整理耗时等问题目前是合理推测，应通过真实工作样本确认严重程度。

### 业务产品结构与软件边界

| 附件中的业务产品 | 附件中的核心结果 | 工作台建议承接 |
| --- | --- | --- |
| AI诊断 | 事实地图、场景池、主场景建议 | 访谈、诊断资料与场景记录 |
| 单场景试点 | 一个可验收的小闭环 | 任务、样本、基线和试点证据 |
| 多部门改造 | 工作流固化与部门复制 | 复用模板、项目关联与变更 |
| 年度运营 | 采用、质量、ROI与版本运营 | 复盘资料和变更记录 |

【已确认事实｜S1 第四节】收费按范围、深度、周期、样本、集成、风险或年度服务组织，未给出具体价格。【本稿建议】第一版不开发报价、合同、财务和计费系统。

### 必须保留的评审门槛

【已确认事实｜S1 第三及第六节】每阶段先完成模板，再开评审会，不能用口头说明替代交付物。所有必须项满足、总分不低于80且无红线，才算通过。70至79分只能有条件通过：写明缺口责任人、完成日期和验证方式，关闭后复审。低于70分、触发红线或缺少关键责任人，不进入下一阶段。阶段未通过须留在本阶段整改；通过后更新00A项目主控台的负责人、日期、状态、证据和决策。

【本稿建议】将“有条件通过”与“允许推进”分开；按原文保守实现为整改关闭并复审通过后才允许推进。若业务方希望例外并行，需另行明确授权人和规则，不能默认为系统允许。

### 阶段状态与人工权限

【本稿建议】阶段状态采用未开始、进行中、待评审、整改中、已通过；项目可另设暂停和终止。评审记录独立保存分数、必须项检查、红线、评审人、日期、证据和结论。修改已通过阶段时保留历史版本并重新评审，避免直接覆盖旧结论。

【已确认事实｜S1】隐私、商业秘密、财务、法律、对外发送、合同承诺和不可逆动作须保留人工审批。【待确认】四层验收的具体四层、各阶段评分权重和红线细目在总目录中未展开，必须取得阶段手册和评分表后再配置。

## 03 建议的 MVP 范围与完成标准

【讨论建议与本稿建议】先形成“建项目 → 更新任务与阶段 → 关联资料与证据 → 人工评审 → AI读取上下文并生成下一步草稿”的最小闭环。九阶段先共用一套数据结构和检查机制，不一次开发九套专属业务应用。

| 优先级 | 范围 | 交付边界 |
| --- | --- | --- |
| MVP必须有 | 客户与项目、成员与基础权限 | 客户只保留项目归属所需字段；按项目限制访问 |
| MVP必须有 | 九阶段、任务、评审与变更留痕 | 阶段材料可用附件或链接；不必在线重建所有模板 |
| MVP必须有 | 项目文档、证据、决策与风险 | 可检索、可追溯来源与版本，支持手工整理 |
| MVP必须有 | AI项目问答与进展摘要 | 只读检索，返回来源、更新时间与缺失信息 |
| MVP必须有 | 导出与恢复验证 | 可导出项目结构化记录及资料清单；验证恢复 |
| V1再评估 | 周报、会议准备、模板辅助填写 | 以MVP资料质量和真实频次决定优先级 |
| 后续再评估 | Obsidian同步、语义检索、客户门户 | 先验证必要性，再确定集成与权限 |
| 首版不做 | 复杂Agent、自动发布、财务计费、全公司流程 | 不得由演示需求扩张为平台级建设 |

### 建议验收场景

A 项目记录：用一个经授权的脱敏样例创建客户和项目，设置负责人、当前阶段、任务、资料及风险；刷新和重新登录后记录仍在，变更可追溯。

B 阶段门槛：分别验证80分且必须项齐全且无红线、75分待整改、低于70分、缺责任人、触发红线等情形。仅满足通过条件的评审允许推进；整改后保留复审记录。

C AI可信度：准备10个有标准依据的问题，覆盖进展、下一步、资料缺失、相互冲突、过期资料和越权询问。已知答案能定位到正确项目的记录或文档；没有证据时明确不足；不得编造进度、跨项目泄漏或自行改写事实。此数量是建议评测规模，不是已达成结果。

D 可接管性：AI失败时仍能查看与更新项目。检索失败和权限不足有明确提示。完成一次备份恢复核对，证明项目、资料关联和权限未丢失。

E 使用价值：请两名拟用人员独立完成查进度、找证据和准备交接摘要，记录耗时、错误与阻碍；若首版仅一人使用则调整样本。具体节省时间目标应先测现状，再由业务方确定。

## 04 核心用户 使用场景与模块

【讨论建议】首批用户为内部项目团队；具体人数、岗位和访问设备尚未确认。下列角色是职责划分，不要求每个角色配备独立人员。

| 角色 | 高频场景 | 建议权限 |
| --- | --- | --- |
| 业务负责人 | 查看全部项目风险、资源与阶段评审 | 授权范围内查看和审批；不绕过业务门槛 |
| 项目负责人 | 维护状态、分派任务、提交材料和评审 | 编辑本项目；重要结论由指定评审人确认 |
| 实施或交付成员 | 记录执行结果、上传证据、查阅SOP | 编辑分配范围，查看有权限的项目资料 |
| 评审人 | 检查必须项、评分、红线与整改 | 提交评审结论，保留签名身份和时间 |
| 客户人员 | 未来确认资料或查看进展 | 首版暂不开放，后续定义可见范围 |

### 首页与项目列表

【本稿建议】首页突出我负责的项目、待办、待评审和阻塞；列表显示客户、项目、阶段、负责人、最近更新时间、下一步及关键风险。暂不显示未经定义的完成百分比，避免任务完成率被误认为业务验收进度。

### 项目详情与阶段执行

【本稿建议】项目详情包含概览、九阶段、任务、文档与证据、决策与风险、AI助手和历史记录。阶段页将模板入口、必需材料、负责人、截止日期和评审结果放在一起；缺失材料应能直接跳转处理。

### 文档与知识模块

【本稿建议】先提供资料登记、上传或授权链接、类型、版本、所属项目及阶段、保密级别、来源和检索。文件原件与AI提炼摘要并存，摘要不覆盖原文。失效链接和解析失败必须可见。

### AI助手与行动草稿

【讨论建议】支持“做到哪里了”“下一步做什么”“准备项目会议”等场景。【本稿建议】MVP先实现进度问答和摘要；建议行动经过人工确认才转成任务，AI生成的风险和决策候选不直接成为正式记录。

### 界面体验与设计验收

【已确认事实】用户希望漂亮。【本稿建议】采用现代、简洁、专业的视觉方向，优先保证信息层级、中文可读性、状态可辨识和常用操作易找；颜色之外同时使用文字状态。先做首页、项目详情、阶段评审三个关键页面原型，以真实长度的脱敏内容检查。品牌色、参考界面、桌面或移动优先级由负责人确认。

## 05 数据模型与系统架构初步设想

【本稿建议】以下是职责草案，不是已经选定的技术栈。先验证多人协作、资料规模、部署条件及权限，再确定实现方式。

| 数据对象 | 主要字段或关系 |
| --- | --- |
| 客户与项目 | Company → 多个Project；项目含范围、Owner、状态、当前阶段、下一步、更新时间 |
| 成员与权限 | User与ProjectMember关联；角色、可访问项目、操作权限；服务端校验 |
| 阶段与任务 | Project → 9个StageInstance；模板版本、任务、负责人、日期、状态、依赖 |
| 文档与证据 | Document记录原件位置、版本、来源、项目、阶段、密级；Evidence关联具体结论 |
| 评审与决策 | Review含分数、必须项、红线、评审人、整改及证据；Decision记录结论和依据 |
| 风险与历史 | Risk含影响、负责人、处置和状态；AuditEvent保存关键变更前后值与操作者 |
| AI请求与产物 | 请求人、项目、引用记录或文档版本、生成时间、模型标识、输出及人工确认状态 |

### 建议的系统职责链

用户 → 工作台界面 → 业务服务与权限检查 → 项目数据库及文件存储。AI请求另外进入上下文组装服务：按项目和权限读取事实与资料 → 组装有限上下文 → 调用模型 → 返回带来源的回答。AI不直接连接所有客户的资料库。

关系型数据库：保存项目状态、任务、成员权限、评审和关联关系，作为结构化事实源。文件存储：保存原件和必要版本，数据库登记其位置和访问权限。检索索引：保存可重建的文本及索引，不作为唯一资料源。

### 实现路径比较与推荐

【本稿建议】若目标是先验证工作方式，可使用现有协作工具加结构化字段和文档链接，验证成本低但定制交互有限。若确认需要持续多人使用、严格评审门槛和集成AI，则建设轻量Web应用、关系型数据库和文件存储。先采用单一应用服务，避免过早拆分微服务。

个人离线试验可以先用本地文件或轻量数据库；团队正式使用需考虑并发、权限和备份。云端托管便于协作，但资料处理范围和服务费用需核对；本地或私网部署也有运维、访问和恢复成本。当前不确定具体供应商、框架或费用。

### 进入实现前要补齐

明确数据字典、唯一标识、必填规则、状态转换、谁有最终写入权、版本与删除策略；用脱敏样例走通一个项目，再冻结首轮结构。仓库、部署环境、域名、账号、CI与运维负责人目前均未验证，不能视为接手即用。

## 06 Obsidian 数据库与 AI Context 的角色

### Obsidian是可选知识入口

【已确认事实｜S2】用户提出“可能还想接Obsidian”，并未决定必须集成。【讨论建议】Obsidian可管理方法论、访谈纪要、SOP和项目经验。【本稿建议】MVP先支持Markdown导入或项目资料链接；只有真实使用证明需要，才开发持续同步。

项目阶段、任务状态、权限及评审结果在业务数据库维护；Obsidian中的状态摘要仅作副本并注明更新时间。不要让数据库和笔记同时无约束地修改同一个正式字段。若以后双向同步，必须补齐稳定ID、版本、冲突处理、删除传播和回滚规则。

### AI Context是每次回答需要的材料组合

【本稿建议】AI Context不是独立事实库，也不是把所有历史文档塞进提示词。每次请求依据用户、项目、问题和权限，读取最新结构化状态，再选取相关文档片段和证据；保留来源、版本、时间和缺失项。模型调用结束后按保留策略记录必要元数据。

| 上下文组成 | 应包含的信息 |
| --- | --- |
| 项目事实快照 | 项目ID、当前阶段、负责人、更新时点、任务、风险、正式决策和评审结论 |
| 相关知识与证据 | 文档ID、版本、标题、段落或位置、来源时间与可访问链接 |
| 回答约束 | 仅限授权项目；事实与建议分开；缺信息时说明；不能自动审批或对外发送 |

### 主要风险与控制建议

范围膨胀：九阶段管理容易扩张成九套自动化业务。首版用通用记录和文件关联承接，新增功能需说明用户场景、验收方式与被替换的优先项。

资料失真或过期：人员不更新时，AI无法保证进展正确。设置更新时间、维护责任人和过期提示；摘要附来源，不用虚构完成率营造确定性。

资料隔离失败：权限应在服务端查询与下载时执行，不能只隐藏页面。用不同项目和角色验证越权访问；文件链接、检索结果和AI引用都要检查。

人机权责不清：AI只提供候选结论和草稿；业务审批、对外发送、合同承诺、生产切换和不可逆操作保留人工审批及记录。

集成返工：先建立资料清单与单一事实源，再决定同步；外部API、价格和账号权限在选型时重新核验，本稿不承诺任何平台现有能力。

维护和退出困难：从首版明确备份、导出、恢复、文档版本及交接责任，确保换人或停用某一模型后，项目资料仍可取回和继续使用。
